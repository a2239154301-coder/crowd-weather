## 1. レビューで指摘されたこと

### レビューを依頼したエンジニア

レビューでの指摘は次の2点でした。

1. **アプリ内で使うモデルを、用途ごとに適材適所で切り替えられる形にすべき**
2. **何をすべきかは既存の構成次第。まず今のテックスタックを明示してほしい**

**この2つの問いへの回答が、この文書の目的です。**
「適材適所の切り替え」は §5 の `lib/ai/orca.ts` で実装済み。「既存の構成」は §3 に全部書きました。

### 原案者による事前分析（要旨）

- 現在のCROWD WEATHERは**「AI SaaS」ではない**。予測値を外部APIやAIに取りに行っていない
- 混雑予測は「チケット数 → 時間帯別の混雑係数 → 会場ゾーンごとの係数 → 天候・開場・退場などの補正 → 混雑度」という**ルールベースの数理モデル**
- WBGTも「気温 × 日射 × 日陰 × ゾーン特性」から算出
- コード内に `OCC`（時間別混雑率）、`SOLAR`（日射係数）、`density()`、`wbgt()`、`isShaded()`、`gateWait()` が直接書かれている
- **「AIが予測している」というより「イベント運営の知見を数式化したシミュレーター」に近い。プロトタイプとしてはむしろ良い**
- 提案構成: 今のTSXに直接突っ込むより、`lib/ai/orca-router.ts` と API層を追加する形がよい
- Orca Routerとの相性: 通常の問い合わせ→安いモデル、混雑予測分析→高性能、イベント運営判断→高性能、大量リクエスト→コスト重視

**この分析は正確で、提案構成もそのまま採用しました。**

そして重要なのは、**「AI SaaSではない」ことが弱点ではなく、そのまま審査項目⑥（LLMコスト）の武器になる**ということです。⑥の配点は「LLMを使わない箇所を意図して設計できているか」を見ています。主処理をLLMに投げていないのは、この項目では満点方向の設計です。

## 4. 各層の解説

### 4-1. 予測層 `lib/forecast/` — LLMを使わない

**なぜLLMを使わないのか。** 混雑指数もWBGTも日陰も、入力が決まれば答えが1つに決まる計算です。LLMに投げると①原価が乗る ②毎回答えが変わる ③根拠を説明できない、の3つを同時に損します。ここは決定的な関数で書くのが正しい。

#### `venue.ts` — 会場の幾何

会場を「ゾーンの集合＋建物の集合＋地面の集合」として持ちます。

```ts
type Zone = {
  id, name, kind,        // kind: stage/gate/queue/corridor/station/alley/indoor/aid
  base: number,          // そのゾーン固有の混みやすさ係数
  shape: Point[],        // 実際の多角形（長方形ではない）
  roofed?: boolean,      // 屋根の下＝常時日陰
}
type Building = {
  shape: Point[],        // 平面の footprint
  height: number,        // m。影の長さを決める
}
```

**重要**: 優先01（会場資料の読解）が最終的に生成するのは、**この `Venue` 型のJSON**です。つまり出力先のデータ構造を先に確定させてあり、AI側は「この形に落とす」だけになります。

デモ用の会場は**架空**（みなと臨海公園 特設会場）。実在会場の警備配置を公開リポジトリとデモ動画に出さないためです。

#### `solar.ts` — 太陽位置

NOAAの近似式で、緯度経度・日付・時刻から**方位角と高度**を計算します。

**検証**: 東京の冬至の南中高度が **30.7°**。理論値は `90 − 35.65（緯度） − 23.44（地軸傾斜） = 30.9°` で一致します。8/9の日の入りも18:45で実際と整合。

#### `model.ts` — 影と混雑と暑熱

**影の計算がこのプロダクトの技術的な核です。**

1. 建物の footprint を、太陽と反対方向に `高さ ÷ tan(太陽高度)` だけ平行移動する
2. 元の footprint と移動後を合わせた点群の**凸包**をとる → それが影の多角形
3. ゾーンを7×7の格子でサンプリングし、**影に入っているセルの割合**＝日陰率を出す

なぜ面積比なのか。最初は「ゾーンの重心が影の中にあるか」の二値判定にしていましたが、**日陰率が30%に張り付いて時間を進めても動きませんでした**。半分だけ影がかかった状態が数字に出ないからです。面積比にしたら滑らかに動くようになりました。

| 時刻 | 11 | 13 | 14 | 15 | 16 | 18 | 19 |
|---|---|---|---|---|---|---|---|
| 日陰率 | 30% | 30% | 31% | 35% | 40% | 47% | 100% |

**昼に日陰がほぼ無いのは演出ではなく計算結果です。** 太陽高度が70°もあれば影は建物の足元にしかできません。これは企画書の「日陰が最少の時間帯。屋内サブステージ・救護所を退避先に」という主張と一致します。

そして**画面に描く影とWBGTに効く日陰判定が同じ関数から出ている**ので、絵と数字が食い違いません。

#### `heatfield.ts` — 連続ヒートマップ

ゾーン単位の代表値ではなく、会場を **125×88の格子（8px）** に切って1セルずつ暑さ指数を計算します。

入力: 日時・緯度経度・気温・湿度・雲量・風向・風速

| 織り込んでいるもの | 内容 |
|---|---|
| 建物の影 | `solar.ts` の実太陽位置から算出 |
| 地表面の材質 | アスファルト1.25 / デッキ1.05 / 芝0.62 / 水面0.28。日射の効き方が変わる |
| 風による冷却 | 風速の平方根に比例。最大 −2.4℃ |
| 建物風下の淀み | 風上へレイを飛ばし、建物に当たるまでの距離で「風の当たりやすさ」を出す。近いほど熱がこもる |
| 風下への移流 | 風上セルの値を3回混ぜ込む。熱が風下へ流れる |

**WBGTの式について（正直に書きます）**

正式なWBGTは**黒球温度の実測**が必要で、気温と湿度だけからは求められません。
よく引用される屋内近似式 `0.567·Ta + 0.393·e + 3.94` を最初に使いましたが、34℃/65%で **36.8℃** となり、環境省の暑さ指数表より数℃高く出て**全面が「危険」で潰れました**。

そこで、日陰・弱風時の値が環境省の区分と整合するよう校正した近似に置き換えています。

```
WBGT_日陰 ≒ 0.70 × 気温 + 0.06 × 湿度 + 0.8
```

校正の目標値: 34℃/65% 日陰→28.5（厳重警戒）／直射のアスファルト→32.5（危険）／28℃/60% 日陰→24（涼）
日なたと日陰の差3〜4℃は、環境省が示す「2〜3℃以上」と同じ桁です。

現在の出力レンジは **27.1〜31.1℃**で、警戒／厳重警戒／危険の3帯が分布します。
この「実式・校正した近似・簡易モデル・未実装」の区別は、**画面上にも常時表示**しています。

#### `scales.ts` — 色

段階色は `dataviz` の `validate_palette.js` で識別性を計測してから決めました（surface `#121826` に対して）。

| 尺度 | 段階 | 隣接ΔE（正常視 / 色覚型） |
|---|---|---|
| 混雑 | `#22C55E` 快適 → `#FDE047` 注意 → `#FB7A1E` 混雑 → `#E5254A` 危険 | 16.6 / 8.9 |
| 暑熱 | `#38BDF8` 涼 → `#A3E635` 警戒 → `#FB923C` 厳重警戒 → `#EF4444` 危険 | 16.2 / 8.6 |

最初の案は隣接色が近すぎて検証に落ちたので差し替えています。危険域には45°のハッチを重ね、**band名を必ず併記**して色だけに意味を持たせません。2つの尺度は**同時に描きません**（レイヤ切替）。同時に出すと赤どうしが衝突します。

### 4-2. 判断層 `lib/ai/` — ここだけがLLMを使う

呼び出し側は `callOrca({ task: "advice", system, user })` としか書きません。モデルの選び方・フォールバック・使用量の回収は全部この中です。

**外部エンジニアの「適材適所で切り替え」への回答が、この `ROUTING` テーブルです。**

| task | 用途 | 頻度 | 第一候補（実測で選定） | フォールバック |
|---|---|---|---|---|
| `advice` | 予報値 → 運営判断 | イベント中・数回 | `google/gemini-2.5-flash-lite`（**2.48秒**） | `openai/gpt-4o-mini` → `anthropic/claude-haiku-4.5` |
| `ingest` | 会場図面・過去計画書の読解 | 会場ごと1回 | `google/gemini-2.5-pro`（Vision + JSON Schema） | `openai/gpt-4o` |
| `plan` | 雑踏警備計画書の起草 | イベントごと数回 | `anthropic/claude-sonnet-4.6`（18.7秒だが最も詳細） | `openai/gpt-4o` → `google/gemini-2.5-flash` |

方針を変えたいときは、この1箇所を書き換えるだけです。将来的にはOrcaRouterのダッシュボードで「名前付きルーター」を作り、`orcarouter/<name>` に差し替えれば**コードを触らずに**方針を変えられます。

## 5. OrcaRouterの使い方と、実測でわかったこと

### 導入は `base_url` の差し替えだけ

```
https://api.orcarouter.ai/v1
Authorization: Bearer sk-orca-...
```

OpenAI互換なので、既存のSDK・モデル名・ストリーミングがそのまま動きます。利用可能モデルは **182件**（`GET /v1/models` で確認済み）。

### `orcarouter/auto` を採用しなかった理由

`auto` の既定戦略は cheapest（トークン単価が最安のモデルを選ぶ）です。**同じプロンプトで9モデルを実測しました**（`scripts/bench.mjs`）。

| モデル | 秒 | 出力トークン | 本文字数 | 判定 |
|---|---|---|---|---|
| `google/gemini-2.5-flash-lite` | **2.48** | 342 | 562 | ✅ 採用 |
| `openai/gpt-4o-mini` | 3.04 | 224 | 299 | ✅ fallback 1段目 |
| `anthropic/claude-haiku-4.5` | 8.45 | 631 | 667 | ✅ fallback 2段目 |
| `anthropic/claude-sonnet-4.6` | 18.73 | 700 | 760 | plan タスクで採用 |
| `google/gemini-2.5-flash` | 5.85 | 696 | 58 | ⚠️ 本文が切れる |
| `openai/gpt-5-mini` | 7.92 | 700 | **0** | ❌ 本文ゼロ |
| `deepseek/deepseek-v4-flash` | 7.43 | 700 | **0** | ❌ 本文ゼロ |
| **`orcarouter/auto`** | **45.96** | **2,620** | 462 | ❌ `qwen/qwen3.7-plus` に解決 |

**結論: トークン単価が最安 ≠ 1リクエストの総コストが最安。**
最安モデルが推論モデルだったため、単価は安くても総トークン数と待ち時間が跳ねました。46秒待つデモは成立しません。

これは弱点ではなく、**実測に基づく設計判断として審査項目⑤⑥でそのまま語れます。** 計測スクリプトはリポジトリに残してあり、いつでも再現できます。

### もう1つの罠: `max_tokens` が小さいと本文が0字で返る

推論モデルは thinking にトークンを使い切り、**本文が空のまま HTTP 200 で返ります**（`gpt-5-mini`・`deepseek-v4-flash` が該当）。エラーが出ないので気づけません。モデルを差し替えたら必ず**本文の字数**を確認してください。

### フォールバックは自前実装

OrcaRouterの `models` + `route:"fallback"` を生HTTPで検証しましたが、`extra_body` にネストしてもトップレベルに置いても**鎖を付けない場合と挙動が変わりませんでした**（存在しないモデル名→503、存在しないルーター名→400。いずれも次候補へ切り替わらず）。

ゲートウェイの機能を否定するものではありませんが、**デモ当日の可用性を、検証できない仕組みに預けない**方針で `lib/ai/orca.ts` のループとして実装しました。第一候補を壊して HTTP 200・`fallbackLevel: 1` で応答することを確認済みです。

※ この挙動はOrcaRouterのサポートチャンネルで確認する予定です。

### ルーティングをブラックボックスにしない

レスポンスの `X-Orca-Resolved-Model` / `X-Orca-Router` ヘッダと `usage` オブジェクトを回収し、**「この提案を処理したモデル」「入出力トークン数」「レイテンシ」を画面に表示**しています。審査項目⑥の実測原価は、この値をそのまま積算して出します。

### モデルIDの注意

スポンサーdeckの記載（`anthropic/claude-opus-5` 等）と公式docsの記載（`anthropic/claude-sonnet-4.6` 等）が食い違っていました。`GET /v1/models` で確認した結果、**deckが正しく公式docsが古い**（182件すべて実在）。新しいモデルIDを使う前に `/v1/models` を叩く習慣は維持します。

また、deckの「約40%削減」「判定<1ms」「RouterArena 1位」は公式docsに裏付けがないため、**審査で出す数字は全て自前の実測**にします。

## 6. 意図的に作らないもの

**説明できることが加点になります。** 「作れなかった」ではなく「作らないと決めた」を示します。

| 作らないもの | 理由 |

## 8. エンジニア（外部エンジニア）に入ってもらうべきか

**結論: 今回のハッカソン期間は「フル参加」ではなく「1回のアーキテクチャレビュー」を依頼するのが最適。**

| 観点 | 状況 |
|---|---|
| そのエンジニアの強み | バックエンドとDB設計 |
| 今回作るもの | **DBなし**のフロント＋APIルート4本。外部エンジニアの強みが最も効く領域を、意図的にスコープ外にしている |
| 残り時間 | 6日。新メンバーの環境構築・仕様共有のコストが、得られる工数を上回りやすい |
| 体制 | 2名。実装担当（AI開発経験あり）＋原案者（営業・提案・プロデュース）。実装はAI支援で回る規模 |
| 審査8項目 | コードで殴れるのは③④⑤⑥⑦。①②⑧は原案者の領域（一次情報・ビジネス・構想）で、そこが既に強い |

**依頼するとしたらここ**: 08-12〜13に**アーキテクチャとセキュリティ設計を1時間レビュー**してもらう。ブース審査と質疑（3分）で技術的に突っ込まれたときの備えになり、費用対効果が最も高い。

**本格参加は受賞後**: 「複数会場・複数イベントの継続運用」に進む段階で、バックエンドとDB設計を本職に任せる、という握り方が自然です。
