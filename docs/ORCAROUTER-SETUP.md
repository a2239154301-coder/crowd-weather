# OrcaRouter の設定（ダッシュボード側）

> **この文書がある理由**: OrcaRouterの設定はダッシュボード側にあり、**リポジトリのコードを読んでも
> 見えません**。コードから分かるのは「`orcarouter/cw-advice` という名前を呼んでいる」ことまでで、
> そのルーターが何を許可し、どの戦略で選んでいるかは外からは確認できません。
> ここに設定内容を書き出すことで、コードと突き合わせて検証できるようにしています。
>
> 最終更新 2026-08-15。設定の実施者=チーム。値の確認は本日再実測済み（§4）。

---

## 1. 名前付きルーター `cw-advice`

コード側の参照箇所: `lib/ai/orca.ts` の `ROUTING.advice.model`

| 項目 | 設定値 |
|---|---|
| ルーター名 | `cw-advice` |
| 許可モデル | `google/gemini-2.5-flash-lite` / `openai/gpt-4o-mini` / `anthropic/claude-haiku-4.5` |
| 戦略 | 最安値優先（cheapest） |

**なぜ許可モデルを3つに絞るのか。** 無制限の `orcarouter/auto`（既定=cheapest）は実測で
`qwen/qwen3.7-plus` に解決し、**45.96秒・出力2,620トークン**を消費しました。同じプロンプトで
`google/gemini-2.5-flash-lite` は 2.48秒・342トークン。最安モデルが推論モデルだと、
トークン単価が安くても総トークンと待ち時間が跳ねます。

そこで「**速いと実測で確認済みのモデルの中で最安を選ぶ**」という形にしています。
autoの利点（自動で安く）は残しつつ、45秒の事故を防ぐ設計です。

**コードを触らずに方針を変えられる**のがこの仕組みの利点で、モデルの入れ替えは
ダッシュボード側で完結します。ただし切り替え前には必ず `scripts/router-check.mjs` で
実測してください（§4）。

## 1.5 APIキーの支出上限・有効期限（2026-08-15 追加）

**やった動機**: この時点でキーの累計消費は$2.35（約¥352・3,000円クレジットの約12%）だった一方、
**支出上限が実質未設定**（`limitUsd: 100000000`）だったことに気づいた。README・記事にデモの
合言葉を明記しているため、鍵の管理ミスというより「合言葉さえ知れば誰でもAIを呼べる」設計を
自覚した上で、キー単体にも上限を持たせておく判断。

| 項目 | 状態 |
|---|---|
| Credit limit（支出上限） | **設定済み: $20**（約¥3,000）。キー編集画面の「Credit limit」欄 |
| Expiration（有効期限） | **設定できなかった**。「無し（never）」から変更しようとしたが、
  ダッシュボードのUI上で変更を受け付けなかった |

### なぜ有効期限だけ変更できなかったか

公式docsでは、キーに設定できる項目として **Credit limit** と **Expiration** の両方が並記されているが、
その節の見出しは **"Per-key options at **creation**"**（＝キー作成時の選択肢）。一方 Credit limit は
別の節で明示的に「create **or edit**」と書かれている。

つまり **Expiration はキー作成時にしか選べず、既存キーを後から編集する経路が無い**設計である
可能性が高い。今回使っているキーは無期限で作成済みのため、変更を受け付けなかったのはこの仕様の
帰結と考えられる（未確認: 公式サポートへの問い合わせはしていない）。

**対応**: 有効期限による保護は諦め、Credit limitで実害の上限を切ることに一本化した。
根本的に有効期限を持たせたい場合は、Expirationを指定して**新しいキーを作り直し、ローテーション
する**必要があるが、締切直前の作業としてはリスクが上回ると判断し見送った。

### ★ アプリの使用量パネルには反映されない（別の値を見ている）

`/api/usage`（`app/api/usage/route.ts`）が表示する `limitUsd` は
`GET /v1/dashboard/billing/subscription` の `hard_limit_usd`（**ワークスペースの契約上限**）であり、
今回キーに設定した `credit_limit_usd`（**キー単体の上限**）とは別の値。そのため画面上の表示は
今回の変更後も変わらない。これはバグではなく参照しているフィールドが違うだけだが、
紛らわしいので明記しておく。

## 2. Guardrails（PII Shield）

来場者の問い合わせやスタッフの自由文報告に個人情報が混ざったとき、**LLMに届く前に伏せ字**にします。
アプリのコードは変更不要で、キーに紐づけた次のリクエストから有効になります。

| 項目 | 設定値 |
|---|---|
| ベース | PII Shield テンプレート（メール・電話・SSN・クレジットカード・IPアドレス） |
| 追加した検出器 | `jp_mobile` → パターン `0[789]0[-\s]?\d{4}[-\s]?\d{4}` → `[PHONE]` に置換 |
| **追加ルール（2026-08-15）** | `max_chars` ── ステージ input・アクション block・上限 **50,000文字**。
  課金される前に長大なプロンプトを拒否する（コスト暴走対策） |
| 適用先 | APIキーに紐づけ（既存のPII Shield guardrailに1ルールとして追加。
  キーに付けられるguardrailは1つのため、新規作成ではなく既存へ追記した） |

### ★ 標準設定のままでは、日本の携帯番号が素通しします

実測で見つけた穴です。標準の `phone` 検出器に `080-1234-5678` 等を投げたところ、
**4形式すべてマスクされずに通りました**（2026-08-13 実測）。上記のカスタム検出器を追加した後、
`080-1234-5678` / `08012345678` / `080 1234 5678` / `090-…` の4形式がマスクされることを
確認しています。

日本のサービスでPII Shieldを使う場合、**標準テンプレートだけでは不十分**という一般化できる知見です。

### 設定時の注意（実際に踏んだもの）

- **Developer以上の権限が必要**。`sk-orca-…` で始まる通信用のキーでは、ポリシーの作成も
  アタッチもできません
- **新しいキーは何も引き継ぎません**。キーを再発行したら明示的にアタッチし直す必要があります
- **一度アタッチしたものを「無効化」しても既定には戻りません**。disableは「そのキーだけ保護なし」に
  なるため、既定へ戻すときは無効化ではなく**クリア（未設定に戻す）**を選びます

## 3. Agent Firewall

**本番の運用モード: 監視のみ（audit-only）。**

| 項目 | 状態 |
|---|---|
| 対象 | `/api/propose`（配置提案）のツール呼び出し `propose_dispatch` |
| 遮断能力 | **実測で確認済み**（`scripts/firewall-check.mjs --expect-deny`） |
| 本番の運用 | 監視のみ。遮断は有効化していない |

### 管轄範囲に注意

Agent Firewallは**ツール呼び出しだけ**を管轄します。通常の文章生成（`/api/plan` や
`/api/advice` のような形）は**Firewallの対象外**で、そちらはGuardrailsの担当です。

このため `/api/propose` を構造化出力（`response_format`）から**ツール呼び出しに作り変えて**、
初めてFirewallの検査対象に入りました（`lib/ai/orca.ts` の単一tool強制呼び出し）。

### 遮断は、公式ドキュメントと違う形で返ってくる

公式docsは「遮断時はHTTP 400」と記載していますが、**応答段階の遮断は別の形**でした（実測）。

```
HTTP 200
finish_reason: "content_filter"
content: "[blocked by workspace firewall policy: ...]"
```

これを検出しないと「JSONパース失敗」という**まったく別の場所のエラー**として現れ、
原因に辿り着けません。`lib/ai/orca.ts` の `attempt()` にこの検出を実装しています
（403の `OrcaError` として扱い、リトライ対象には含めない）。

### なぜ監視モードに留めているか（正直な理由）

提案データが配列（`proposals[]`）構造のため、「実在しないゾーンのときだけ拒否」という
`args_match_json` 条件を配列に対して正確に組む検証時間が確保できませんでした。
**誤設定は正常な提案まで全部弾く事故**になります。

OrcaRouter公式が推奨する段階的展開（observe → shadow → enforce）の **observe段階**に
留める、という判断です。完全な遮断運用は次の課題として明示します。

なお、**遮断能力そのものは実測で証明済み**であり、監視モードで通常の呼び出しが正常に通ることも
確認しています。

## 3.5 データ保持（Zero Data Retention・2026-08-15 確認）

プロンプト・出力本文はゲートウェイの既定でディスクに保存されない（Zero Data Retentionが既定オン）。
別枠でオプトインの「トラブルシュート用の生ログ保存」機能があり、こちらは**既定オフ**。

Settings → Privacy で確認したところ、**既定のオフのままだった**（変更なし）。誤ってオンに
していないことの確認のみで、設定作業は発生していない。

## 4. 設定が効いていることの確認方法

いずれもリポジトリ内のスクリプトで再現できます（実行には自分のAPIキーが必要）。

```bash
node scripts/router-check.mjs      # 名前付きルーターの疎通とレイテンシ
node scripts/bench.mjs             # モデル別の実測ベンチ（9モデル・課金あり）
node scripts/firewall-check.mjs    # Firewallの疎通（--expect-deny で遮断を検証）
```

### `router-check.mjs` の実測（2026-08-15 実行）

```
== 基準: 直接指定 google/gemini-2.5-flash-lite ==
   200 1427ms 本文71字

== 検証: orcarouter/cw-advice × 3回 ==
 run1: ✅ 200・90字 / router=cw-advice resolved=google/gemini-2.5-flash-lite / 1677ms
 run2: ✅ 200・46字 / router=cw-advice resolved=google/gemini-2.5-flash-lite / 1114ms
 run3: ✅ 200・44字 / router=cw-advice resolved=google/gemini-2.5-flash-lite / 1075ms
```

**判定基準**: 3回とも ①HTTP 200かつ本文が空でない ②`X-Orca-Router` / `X-Orca-Resolved-Model`
ヘッダが返る ③レイテンシが直接指定の3倍以内、を満たすこと。

`X-Orca-Resolved-Model` が返るため、**ルーターが実際にどのモデルを選んだかが応答ごとに確認でき、
その値を画面にも表示しています**（ルーティングをブラックボックスにしない）。

## 5. アプリ側で持っている設定（コードで確認できるもの）

ダッシュボード側ではなくリポジトリ内にあるものです。対比のために併記します。

| 項目 | 場所 |
|---|---|
| タスク別のモデル振り分け・フォールバック鎖 | `lib/ai/orca.ts` の `ROUTING` |
| フォールバックの実装 | `lib/ai/orca.ts` の `callOrca()`。**OrcaRouterの `models`+`route:"fallback"` は効いている証拠が取れなかったため自前実装**（2026-08-09の判断） |

| デモ用アクセス制御 | 合言葉ゲート。`middleware.ts` がCookieを検証し、`app/api/gate/route.ts` が定数時間比較で照合してHttpOnly Cookieを発行する |
